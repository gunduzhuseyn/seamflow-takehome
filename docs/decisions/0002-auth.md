# Auth

## Context

The app needs to know who a user is and which organization they act
in. A small app needs at most an admin role.

## Decision

Sign-in is required. Auth is always on.

Clerk proves identity only. Users, organizations, memberships, and
roles live in this database and change through this API. No Clerk
organizations, no webhooks.

One Clerk development instance serves every copy of this repository.
Sign-up is open and happens in the app, in the same Clerk component as
sign-in. A new user gets a personal organization on first login, with
the admin role. The seed creates the seed user account through the Clerk backend
API.

## Why

- One vendor handles sign-in, sessions, and tokens.
- The database is the single authority for access. No sync to keep.
- A Clerk development instance works without an owned domain.
- One code path. No auth-off branch to test.
- Open sign-up lets a second user show that one org cannot see another.

## Cost

The Clerk secret key is needed to run the API and the seed. The
development instance shows a banner on the public URL. Roles set in
Clerk have no effect. Copies share one user pool. Anyone with the
public URL can create an account. The development instance has a user
limit. To close sign-up, set the Clerk sign-up mode to Restricted.
The sign-in form tells a visitor whether an email has an account. Every
account here is a test account, so this is accepted. Clerk's strict
enumeration protection removes the leak, but it needs an email code
before the password. The app shows no Clerk account management. The
user data that the app uses changes only through this API.

## How to revert

Replace the Clerk token check in the auth dependency with another
identity source that returns a user id. Tables and scoping stay.
